# fight.c behavioral parity review

Reviewed October 18, 2026. Reference: the local PyRom ROM24 checkout, not a generic upstream ROM distribution. This is an investigation only; no runtime or collection changes were made.

## Scope and interpretation

Compared combat rounds, assistance, hit/damage calculations, safety, defenses, death/corpses, experience, and the implemented combat commands. Followed Python helpers, action execution, message construction, and representative collection documents. Designer-authored guards, payloads, and asynchronous architecture are accepted implementation choices and are not findings in themselves.

The departures below are verified by static inspection unless explicitly marked as unresolved. Whether a gameplay difference is intentional remains unresolved unless documented. In particular, the Python safety code explicitly calls its PK/charm behavior provisional; that establishes incomplete migration, not a documented replacement ruleset.

## Highest-impact departures

1. **Damage bypasses ROM's final safety check.** C:675–776; Combat:614–640. ROM rejects an already-dead victim and calls `is_safe` and `check_killer` inside `damage`. Python proceeds into combat setup and HP subtraction without those checks. Any caller that has not already enforced all protections can damage protected targets; direct damage on an already-dead target can also repeat death handling. Command guards do not replace this final boundary for other callers.

   **Resolved October 18, 2026:** `FightHandler.damage` now returns immediately for missing/dead victims, checks the existing safety helper for attacks on other entities, returns its reason through the normal attacker payload, and invokes the killer hook before combat setup for allowed attacks (including zero damage). Self-damage bypasses hostile checks as in ROM. Focused regressions cover safe rooms, protected NPCs, dead/missing targets, hidden/zero damage, hook ordering, and self-damage. This restores the boundary; the separate safety-rule and killer-hook findings remain open.

2. **Player-killing and charm protections are incomplete.** C:990–1093; Combat:100–144. Python omits the clan requirements, eight-level restriction, killer/thief exceptions, shopkeeper protection, non-owner protection for charmed victims, and restrictions on owned charmed NPCs attacking players. In otherwise equivalent rooms, attacks ROM rejects can pass Python safety. Shop data exists separately, so the absence of a shop check is not explained by missing content.

   **Resolved October 18, 2026:** the existing safety helper now checks the shop registry, charm ownership, owned NPC attacks on players, and player clan/level eligibility with killer/thief exceptions. `CharacterApi.is_clan` uses the existing service `guild` field; independent/loner membership qualifies, matching this checkout's `handler.c` membership check. No content schema or command pipeline changes were needed. All 37 focused combat-safety and character-API tests pass. Item 3's separate safety precedence differences and item 4's spell-specific rules remain open.

3. **Safety precedence also blocks attacks ROM allows.** C:995–1002; Combat:104–143. ROM allows self-damage and existing retaliation before safe-room/protected-NPC checks, and allows sufficiently high immortals to bypass safety. Python rejects self-targets, applies room/protected flags first, and has no immortal override. It also applies a generic kill-stealing restriction to players as well as NPCs; ROM's melee helper does not do so. Self-target command guards may still legitimately reject individual commands; this finding concerns the shared helper.

   **Resolved October 18, 2026:** shared melee safety now permits self-targets and existing retaliation before room/NPC/clan protections, and applies the immortal override only when the attacker is immortal and actual level exceeds the loaded `LEVEL_IMMORTAL` threshold. Safe-room checks now apply to NPC victims and NPC attackers as in ROM; player-versus-player eligibility uses the clan rules. Removed the generic kill-stealing restriction from this helper while preserving existing command guards and the spell caller keyword. Missing-room and dead-target rejection remain before these exceptions. All 45 focused combat and character-API tests pass, including final-damage-boundary retaliation coverage. Spell-specific safety remains item 4.

4. **Spell safety lacks its separate area/group rules.** C:1095–1187; Combat:146–153. Python delegates spell safety to melee safety, adding only area self-exclusion. ROM additionally protects high immortals from area spells, prevents area spells hitting owned charmed mobs even for the owner, restricts NPC area targets by opponent group, and restricts NPC attacks on players outside the opponent's group. Area spell targeting therefore differs in both permitted and excluded targets.

   **Resolved October 18, 2026:** `is_safe_spell` now implements ROM's separate spell policy within the existing combat handler. It preserves area self-exclusion, self/retaliation precedence, and the single-target-only immortal override; checks protected NPCs, pets, charm ownership and player clan eligibility; excludes high immortal area victims; and applies the distinct NPC/player opponent-group rules. Existing area spell callers continue to use this helper without pipeline or content changes. Missing/dead/absent targets remain rejected. All 57 focused combat and character-API tests pass, including an integration test of the real `SpellApi.damage_room_expr` caller skipping protected targets before invoking damage. An attempted broader run including `test_spell_affect_payload_messages` could not import the existing `skill/Spell.py` because its `from_json` return annotation raises `NameError: Spell`; this unrelated import issue was left unchanged.

Off-room and unrelated players receive nothing; NPCs contribute levels without receiving XP; grouped NPC killing blows still reward players. Self-death gives no rewards. Each recipient gets their own XP/level notices through standard payloads, preserved across spell damage, weapon procs, multi-hit aggregation, world pulses, and nested command results; the killer's metadata remains available without emitting duplicate XP notices. Equipment effects are removed and incompatible worn items unequipped, detached, and dropped through existing APIs. Two local-source details are preserved: `group_gain` has no explicit player-victim exclusion despite its introductory comment, and its equipment loop checks the original killer after each player reward, not each recipient. The change does not alter the separate XP-formula/playing-time findings. User-facing reward/zap messages live in the additive optional `GameData.combat.groupRewards` section, loaded by `GameData.from_json`; publish/load that section through the content service for the new messages. The collection CLI dry run validated the change, but its Windows atomic replace failed; the same section was applied in place with full JSON equality checks outside that addition and verified again through collection-query. All 109 focused tests pass across group rewards, combat, weapon effects, character API, GameData, and existing effect utilities. Real advancement and representative collection messages were exercised, with service/network boundaries isolated; syntax and diff checks pass. No live server or content-service deployment was performed.

## Combat calculations and rounds

12. **Parry/dodge use different probabilities and prerequisites.** C:1263–1343; Combat:159–170,222–232. ROM uses half skill, visibility penalties, level difference, and strict `<` success. Unarmed players cannot parry; unarmed NPCs get half parry chance. Python instead adds dexterity, caps parry at 60/dodge at 65, uses `<=`, omits the visibility/level adjustments, and permits unarmed player parries. Example: equal-level, visible, armed characters with 100 skill and 20 dexterity parry at 49% in ROM versus 55% in Python.

   **Resolved October 18, 2026:** parry and dodge now use integer half skill, the ROM visibility halving, the defender-minus-attacker level adjustment, and strict `<` success without a dexterity bonus or probability cap. Unarmed players cannot parry; unarmed NPCs halve their parry chance again. Parry checks attacker visibility of the defender, while dodge checks defender visibility of the attacker, matching the local C source. Awake prerequisites, existing skill payloads, and successful-defense improvement remain in their current paths. The independent skill-value penalties in item 15 remain open.

33. **Death-time item flags are not processed.** C:1490–1530; Combat:455–461,989–994. 34. **Player death has no ROM XP penalty or killer/thief cleanup.** C:874–907; Combat:699–715,1546–1570.    **Resolved October 19, 2026; XP calculation corrected to ROM's total-XP logic:** the level floor is `experience_per_level * level`. Only when `accumulated_experience` exceeds that floor does player death apply `trunc(2 * (floor - accumulated_experience) / 3) + 50` through `CharacterAdvancement`. The comparison and delta use total XP, independently of the `experience` progress field; the earlier progress-only adaptation was incorrect and has been removed. This retains C's signed truncation and possible small positive adjustment near the floor. After raw death processing, a non-self player killer outside the victim's same clan clears killer first, otherwise thief; same-clan kills retain flags, with independent/loner membership treated as independent. Player deaths are logged and all combat deaths return the proper player/mobile wiznet notice through existing recipient filtering. Added boundary tests below/at/above the total-XP floor, divergent progress values, signed rounding, and integration with the real advancement helper. All 198 focused combat tests pass after this correction.

## Remaining uncertainty and validation

- This is a broad static review, not an exhaustive execution proof. Every function family in `fight.c` was located; command guard/message text parity was sampled, not exhaustively enumerated. Kill/murder/rescue/slay and damage-message verb thresholds need a dedicated follow-up comparison before claiming complete parity. Legacy-format NPC/weapon conversion, race-affect restoration, body-part distribution, and full movement-hook behavior remain unverified.
- The C damage cap at 1200 and associated anti-cheat weapon extraction are absent from Python's damage entry point (C:686–702; Combat:614–630). This is a confirmed difference, but whether legacy anti-cheat punishment is desired in the Python product is unresolved; it is not included among the 36 actionable gameplay findings.
- No exemption was inferred merely because behavior is expressed through data. Used the collection-query skill and bundled Python to list snapshots and inspect the full individual `backstab` skill and `flee` command documents, confirming their guards, executor, plan, and payload rather than assuming they were missing.
- Attempted `unittest` for `test_combat_dynamic_commands`, `test_combat_api_dynamic_checks`, and `test_combat_handler_aggression` together. Result: 27 tests reported, two errors: dynamic commands could not import `requests`; a dynamic-check fixture lacked `context.room`. This is not a passing validation run.
- Separate attempts exposed additional test-isolation/import problems: aggression failed importing `Context` with `NameError: Command`; dynamic checks failed importing `registries`. The combined run's successful cases depend on shared module stubs/order and are not evidence of a clean standalone suite.
- Neither gameplay implementation was modified or run as a live server. No regression tests were added for this review. Findings are source-backed discrepancies, not claims that existing tests reproduce them.

Suggested fix order: final damage safety and death item/currency ownership first; group rewards and weapon effects next; then probability formulas, NPC actions/assistance, escape behavior, and message parity. Keep tunable content in collection documents and put shared mechanics in reusable runtime helpers, preserving the designer workflow.
