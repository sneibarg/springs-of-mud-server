## P2 — Strength changes do not force an overweight wielded weapon to drop

Python [EffectHandler.py:181](C:/Users/scott/PycharmProjects/springs-of-mud-server/src/item/EffectHandler.py:181) applies the stat modifier and finishes without rechecking the wielded weapon. Both application and removal go through this path. [Item.py:475](C:/Users/scott/PycharmProjects/springs-of-mud-server/src/item/Item.py:475) already computes the correct effective-strength wield limit, but its runtime use is limited to equipping checks; it is not called after affect changes. Equipment helpers and item-wearer refresh do not supply this transition either.

ROM [handler.c:983](C:/Users/scott/PycharmProjects/PyRom/Rom24/src/handler.c:983) checks a player's wielded weapon after affect modification. When recursive weapon weight exceeds current strength's wield allowance times ten, it removes the weapon from the character, puts it in the room and emits actor/room drop messages, with a recursion guard. NPCs are exempt.

Production-model probe using MovementFixture's initialized game tables and real EffectHandler: a player with strength 20 wielded a weapon weighing 200. `weapon_too_heavy` initially returned false. Applying an APPLY_STR modifier of -10 produced effective strength 10 and `weapon_too_heavy=true`, yet `equipped.wielded` still referenced the weapon and the room did not contain it. This is also the modifier produced by the bundled level-50 weaken definition. Losing a strength buff can encounter the same missing recheck through effect removal.

Consequence: a weakened player keeps attacking with a weapon ROM makes them drop. Add the reusable affect-driven equipment transition, preserving ownership, item-effect removal, NPC exemption and recursion protection. Messages should follow the repository's payload conventions. This is separate from the previously fixed weight check when issuing wear/wield commands.

## P2 — Prompts reveal dark or unseen room information and closed exits

Python [PromptFormat.py:33](C:/Users/scott/PycharmProjects/springs-of-mud-server/src/interp/PromptFormat.py:33) renders `%r` directly from room.name and `%e` from [Room.py:75](C:/Users/scott/PycharmProjects/springs-of-mud-server/src/area/Room.py:75). The latter lists all exit directions, without closed-door, destination-existence or destination-visibility checks. Neither renderer receives the observing character. [MessageBus.py:87](C:/Users/scott/PycharmProjects/springs-of-mud-server/src/server/messaging/MessageBus.py:87) sends this rendered prompt directly; the normal look-command visibility checks do not protect it.

ROM [comm.c:1419](C:/Users/scott/PycharmProjects/PyRom/Rom24/src/comm.c:1419) renders the room-name token as `darkness` when blind or in a dark room, except for player holylight. Its exit token at [comm.c:1358](C:/Users/scott/PycharmProjects/PyRom/Rom24/src/comm.c:1358) requires a destination, allows destination visibility or the specific unblinded-infrared exception, and excludes closed exits. These are visibility semantics, independent of intentional prompt formatting or option-storage differences.

Production-model probe: configure a player's PromptFormat with room_name and exits enabled; set the current room's ROOM_DARK flag, light to zero and name to Secret Hall; close its sole north exit. `room.is_room_dark()` returned true, but render_prompt produced `\r\n< Secret Hall North>`. ROM would conceal the room name and would not list the closed north exit. The player had no holylight exception.

Consequence: prompt options bypass visual exploration restrictions. Make these token renderers observer-aware and apply the reference visibility/door checks; preserve authorized holylight and infrared behavior rather than indiscriminately hiding every exit in darkness.
