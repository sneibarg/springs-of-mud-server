## High-priority findings

1. **[P1] Pickup ignores corpse ownership permissions.** C:58–86,117–121,285–294; Object:370–410,472–490; Commands `get` guards. With another online player's owned corpse, Python checks container type/closed state but never implements `can_loot` for the corpse or the individual object. ROM permits the owner, immortals, eligible group members, or looting authorized through `PLR_CANLOOT`; Python allows unrelated players to take the contents. The recent death code's owner metadata does not enforce pickup permission.

   **Resolved October 19, 2026:** `ItemApi.can_loot` applies ROM's owner-name, immortal, player CANLOOT, same-group, and absent-owner rules. Object commands resolve owners from playing characters and live room occupants, including link-dead players and instantiated NPCs, rather than offline persisted players or NPC prototypes. Both `get` and `take` check player-corpse permissions before closed/missing-content guards, and the shared `_get_one` primitive enforces both container and individual-object ownership for single, bulk, and direct callers. Denial messages remain in command payload data. This change does not address the separate pit, capacity, autosplit, or lookup findings.

Reward formulas and autosplit are unchanged.

## Validation and limitations

Collection inspection used the collection-query workflow: collection inventory, exact command documents/guard paths, item-type counts, GameData item/wear enums, and the blindness spell's lambdas. Loaded item types remain unprefixed through `ItemService` -> `ItemUtil.normalize_item_data` -> `Item.from_json`; this was checked explicitly before reporting type mismatches.

Executed with the bundled Python runtime, in separate processes where test stubs could conflict:

- `python -m unittest tests.test_object_get_dynamic_commands`: **55 tests, 54 pass, one error**. `test_put_into_container_uses_payload_templates` raises `AttributeError` because its `_Container` fixture lacks `is_container`, which the real collection guard calls. This fixture error is not evidence that the real Item method is absent.
- `python -m unittest tests.test_item_util_normalization`: **five pass**.
- `python -m unittest tests.test_object_fountain_commands`: **cannot import**, because its isolated module setup reaches `combat.CombatHandler` -> `MobileApi` and fails with `ModuleNotFoundError: mobile`. No fountain-suite pass is claimed.
- Seven small in-memory probes using the existing isolated object test harness reproduced: canonical `weapon` rejected by shop buy-type checks; `pc_corpse` not recognized; removable right ring not attempted after cursed left ring; pill removed with zero spell calls; poisoned food removed with zero poison joins; weight-1000 object accepted into capacity-10 bag; and `drop 10 silver` leaving 100 silver unchanged with an item-missing message. Probes used minimal collaborators, not a live server, and were not added as implementation tests.

The ordinary shell has no `python` command. The repository `.venv` interpreter cannot import `encodings`; the bundled runtime was used instead. Full-server startup, live content-service responses, asynchronous delivery order, all message variants, every shop grouping edge case, NPC skill formulas, and complete spell-specific behavior were not executed. Normal fountain filling and pouring broadly follow the reference path, but optional filling from an explicitly named drink container extends ROM's fountain-only command; its resource-conservation behavior needs a separate design review if that extension is retained. Staff success learning is also performed once per command in Python versus once per qualifying target in C:2024–2025; this should be covered when fixing item spell execution.

Suggested correction order: ownership/sacrifice protections; consumable effects and container constraints; canonical item type handling; reusable item-spell targeting/safety/retaliation; then theft, currency/pit/autosplit, shop pricing, and equipment/lookup details. Keep message text and tunable content in collections, with shared state transitions and validation in reusable runtime helpers.
